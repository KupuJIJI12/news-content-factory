# NewsContentFactory — спецификация MVP

- **Дата:** 2026-10-23
- **Статус:** на согласовании
- **Автор решений:** владелец проекта (самозанятый, владелец канала в Max)

## 1. Цель и критерии успеха

Автоматизированный конвейер, который собирает новости города из открытых источников, отбирает интересные, склеивает повторы в один сюжет, переписывает их в стиле редакции через LLM, проверяет факты и после одобрения модератором в веб-админке публикует в канал Max.

**MVP:** один город — **Отрадный (Самарская область)**, одна площадка — **канал в Max**.

**Критерии успеха MVP:**
1. Новости из подключённых источников автоматически появляются в админке как готовые черновики без участия человека.
2. Одно событие из нескольких источников даёт **один** сюжет и один пост; повторов в канале нет.
3. В канал уходит **не более 3–4 постов в день** — самые интересные по оценке.
4. Модератор тратит на проверку и публикацию одного поста меньше минуты, в том числе с телефона.
5. В опубликованных постах нет фактов (чисел, дат, имён, адресов), которых нет в источниках.

**Будущее (вне MVP, но архитектура готова):** N городов, публикация в Telegram и VK.

## 2. Ключевые решения

## 5. Модель данных

Все сущности имеют `Id`, `CreatedAt`, `UpdatedAt`. Время хранится в UTC; «день» для лимита и расписания считается в часовом поясе города.

- **City:** `Name`, `Slug`, `TimeZone` (`Europe/Samara`), `Keywords[]` (основы слов для фильтра: «отрадн», …), `ScoreThreshold` (6) — порог интересности для сюжетов города.
- **Source:** `Name`, `Type` (Rss/Html/Vk), `Url`, `Config` (JSON: селекторы HTML или параметры VK), `PollIntervalMinutes` (60), `ExpectedFrequencyHours` (порог детектора тишины), `PhotosAllowedWithCredit` (bool), `PhotoCredit` (текст подписи), `IsEnabled`, `LastRunAt`, `LastSuccessAt`, `LastItemAt`, `ConsecutiveFailures`, `LastError`.
- **SourceCity** (связь многие-ко-многим): `SourceId`, `CityId`, `IsDedicated` (источник целиком про город → фильтр пропускается).
- **RawItem:** `SourceId`, `ExternalId` (уникален в паре с `SourceId`), `Url`, `Title`, `Text`, `PublishedAt`, `CollectedAt`, `ImageUrls[]`, `Status` (New/SkippedOld/Irrelevant/Relevant/Clustered/Failed), `RelevanceReason`, `StoryId?`.
- **Story:** `CityId`, `Summary` (1–2 предложения для склейки), `Score` (1–10), `ScoreReason`, `Status` (см. §6.8), `HasUpdates` (bool), `LastError`.
- **Draft:** `StoryId`, `Version`, `Title`, `Body` (внутренний формат §6.5), `Hashtags[]`, `Author` (Llm | UserId), `RegenerationHint?`, `FactCheckIssues` (JSON), `IsCurrent`.
- **StoryImage:** `StoryId`, `RawItemId?` (null — загружено вручную), `OriginalUrl?`, `LocalPath`, `Credit?`, `IsAllowed` (из флага источника или true для загруженных).
- **Channel:** `CityId`, `Platform` (Max), `Name`, `ExternalChatId`, `DailyLimit` (4), `IsEnabled`.
- **Publication:** `StoryId`, `DraftId`, `ChannelId`, `StoryImageId?`, `ScheduledAt`, `Status` (Scheduled/Sending/Published/Failed/Unknown/Cancelled), `ExternalMessageId?`, `Attempts`, `LastError`, `HangfireJobId`, `PublishedAt?`, `ApprovedByUserId`.
- **User:** `Login`, `PasswordHash`.
- **LlmProvider:** `Name`, `Kind` (OpenAiCompatible/GigaChat), `BaseUrl`, `ApiKeyEnvVar` (имя переменной окружения с ключом), `Models[]`.
- **LlmTaskSetting:** `Task` (Relevance/Clustering/Scoring/Rewrite/FactCheck), `ProviderId`, `Model`, `Temperature`.
- **PromptTemplate:** `Task`, `Version`, `Text`, `IsActive`. В MVP промпты глобальные; привязка стиля к каналу — после MVP.
- **LlmCall:** `Task`, `ProviderId`, `Model`, `StoryId?`, `RawItemId?`, `PromptTokens`, `CompletionTokens`, `LatencyMs`, `Request`, `Response`, `Success`, `Error`.
- **AppSetting:** ключ-значение (`DailyTokenBudget` и т. п.).

## 6. Конвейер

### 6.1 Оркестрация

Задачи Hangfire:
- `CollectSourceJob(sourceId)` — периодическая, по `PollIntervalMinutes` источника.
- `ProcessRawItemJob(rawItemId)` — ставится в очередь после сохранения новой сырой новости: фильтр → склейка.
- `ProcessStoryJob(storyId)` — после создания или обновления сюжета: оценка → рерайт → проверка фактов.
- `PublishJob(publicationId)` — отложенная на `ScheduledAt` или немедленная.

**Склейка сериализуется по городу** (advisory lock PostgreSQL на `CityId`): две новости об одном событии, обработанные параллельно, не должны создать два сюжета.

### 6.2 Сбор

1. Сборщик возвращает список элементов; новые (по уникальному ключу `SourceId + ExternalId`) сохраняются как `RawItem`.
2. **Защита от наводнения:** элементы с `PublishedAt` старше 48 часов сохраняются со статусом `SkippedOld` и дальше не обрабатываются (важно при первом запуске источника).
3. **RSS:** `System.ServiceModel.Syndication`; текст из `content:encoded` → `description`; картинки из `enclosure`/`media:content`/`<img>` в теле. HTML в тексте очищается до простого текста с абзацами.
4. **HTML:** конфиг источника: `listUrl`, `itemSelector`, `linkSelector`, `titleSelector?`, `dateSelector?`, `dateFormat?`, `bodySelector?`, `imageSelector?`. За запуск обрабатывается только первая страница списка; для новых ссылок скачивается статья, текст берётся по `bodySelector`, при его отсутствии — через SmartReader. Парсинг — AngleSharp.
5. **VK:** `wall.get` (последние 20 записей) с сервисным токеном `VK_SERVICE_TOKEN`; короткое имя сообщества резолвится в `owner_id` один раз. Рекламные записи (`marked_as_ads`) пропускаются; у репостов берётся текст оригинала. Заголовок — первое предложение текста. Фото — самый большой размер.
6. Вежливость: таймаут 30 с, не чаще 1 запроса в секунду на домен, User-Agent вида `NewsContentFactory/1.0 (+контакт)`.

### 6.3 Фильтр по городу

1. Если источник помечен `IsDedicated` для города — новость сразу `Relevant`.
2. Иначе — поиск основ из `City.Keywords` в заголовке и тексте (без учёта регистра). Нет совпадений → `Irrelevant`, без вызова LLM.
3. Есть совпадения → LLM (`Relevance`) возвращает `{ "relevant": bool, "reason": string }`. Пример отсева: «трасса "Отрадный — Богатое"» в новости про Борский район.

### 6.4 Склейка в сюжет

1. Кандидаты: все сюжеты города, созданные за последние 72 часа, в любом статусе, кроме `Rejected`.
2. Нет кандидатов → создаётся новый сюжет.
3. Иначе LLM (`Clustering`) получает заголовок и начало текста новой новости и список `{id, summary}` кандидатов; возвращает `{ "storyId": number | null, "reason": string }`. Ответ с `storyId`, которого нет в списке, считается ошибкой валидации.
4. Новый сюжет: `Summary` генерируется в том же запросе (поле `newSummary`).
5. Присоединение к существующему сюжету:
   - статус `New`/`LowInterest`/`ReadyForReview` **и** текущий черновик создан LLM → сюжет заново проходит `ProcessStoryJob` (оценка и черновик пересобираются);
   - текущий черновик правил человек, **или** статус `Scheduled`/`Published` → только `HasUpdates = true`, черновик не трогаем.

### 6.5 Оценка интересности

LLM (`Scoring`) по всем источникам сюжета возвращает `{ "score": 1..10, "reason": string }`. Критерии — в редактируемом промпте; по умолчанию:
- высоко: прямо касается жителей (отключения воды/света/тепла, перекрытия дорог, ЧП, цены, транспорт, ремонт), городские события, необычные истории;
- низко: протокольные мероприятия, поздравления, отчёты чиновников, информационные справки.

`score < City.ScoreThreshold` → статус `LowInterest`, рерайт не запускается (кнопка «Всё равно сгенерировать» в админке). Иначе → рерайт.

### 6.6 Рерайт

LLM (`Rewrite`) получает все тексты сюжета, промпт редакции и необязательную подсказку модератора; возвращает `{ "title": string, "body": string, "hashtags": string[] }` (3–4 хэштега).

Промпт редакции по умолчанию (редактируемый):

> Ты — выпускающий редактор сети городских новостных каналов. Твоя задача — сделать уникальный рерайт текста. Заголовок должен быть завлекающим, отчасти кликбейтом — сильный, цепляющий. Перескажи новость живым, понятным языком. Избегай канцеляризмов вроде «данный», «является», «в целях реализации». Обязательно сохрани все важные факты: даты, точные адреса, имена. Структурируй текст: используй абзацы и списки (буллеты), если это уместно. В конце добавь 3–4 релевантных хэштега (например: #город #новости #чп).

Системная часть, добавляемая всегда: использовать **только** факты из источников; заголовок не должен обещать того, чего нет в тексте; не указывать источники и не ссылаться на другие издания.

**Внутренний формат `body`:** абзацы через пустую строку, `**жирный**`, маркированные списки строками `- `. Без ссылок и прочей разметки. Каждый публикатор конвертирует этот формат в разметку своей площадки.

### 6.7 Проверка фактов

Два слоя, результат пишется в `Draft.FactCheckIssues`:
1. **Детерминированный:** из заголовка и текста черновика извлекаются числа (включая номера домов), даты и время; каждое значение ищется в объединённом тексте источников с нормализацией («15 ноября» ≈ «15.11»). Не найдено → замечание.
2. **LLM (`FactCheck`):** «сверь черновик и заголовок с источниками» → `{ "issues": [ { "claim": string, "problem": string } ] }`. Отдельно проверяется, не преувеличивает ли заголовок.

Замечания не блокируют публикацию; они подсвечиваются в редакторе. После проверки сюжет получает статус `ReadyForReview`.

### 6.8 Статусы сюжета

```
New → Processing → LowInterest
                 → ReadyForReview → Scheduled → Published
                 ↘ ProcessingFailed (кнопка «Повторить»)
ReadyForReview / LowInterest → Rejected
Scheduled → ReadyForReview   (отмена публикации)
Scheduled → PublishFailed    (ошибка или статус Unknown у публикации)
```
Флаг `HasUpdates` ортогонален статусу. Модератор сбрасывает его, когда просмотрел обновления.

### 6.9 Модерация и публикация

- **Действия модератора:** правка (создаёт новую версию `Draft` с `Author = UserId`), «Перегенерировать» с подсказкой, выбор фото, «Отклонить», «Опубликовать сейчас», «Запланировать» (дата/время в часовом поясе города), «Отменить публикацию» для запланированных.
- **Дневной лимит:** для канала считаются публикации со статусами `Published`, `Sending`, `Scheduled` с датой в текущих сутках (часовой пояс города). Если новая публикация превысит `DailyLimit`, UI показывает предупреждение и требует явного подтверждения. Сервер принимает запрос с флагом `overrideLimit = true` и пишет это в журнал.
- **Публикация** (`PublishJob`):
  1. `Publication.Status = Sending` (сохранено в БД **до** обращения к API);
  2. вызов `IPublisher.PublishAsync`;
  3. успех → `Published` + `ExternalMessageId`, сюжет → `Published`;
  4. ошибка API до отправки (сеть, 5xx, 429) → до 3 повторов с нарастающей паузой, затем `Failed`;
  5. при старте или повторе задачи, если запись уже в `Sending` (процесс упал посередине), повторная отправка **не выполняется** → статус `Unknown` («проверьте канал вручную»), сюжет → `PublishFailed`.

## 7. Публикация в Max

- Бот создаётся на платформе MAX для партнёров (профиль самозанятого), проходит модерацию, назначается администратором канала с правом `write`.
- API: `https://platform-api2.max.ru/`, токен в заголовке `Authorization`, лимит 30 запросов/с. Токен — переменная окружения `MAX_BOT_TOKEN`. Один бот обслуживает все каналы; `ExternalChatId` канала хранится в БД.
- Бот только отправляет сообщения: вебхук и long polling не нужны.
- Картинка: загрузка через механизм загрузки вложений Max API, затем отправка сообщения с вложением.
- Конвертер разметки: заголовок — жирная первая строка; `body` → поддерживаемый Max формат (markdown или html); хэштеги — последняя строка; подпись к фото (`Фото: …`), если она есть, — перед хэштегами.

**Проверить на этапе реализации** по документации dev.max.ru: точные эндпоинты отправки сообщения и загрузки картинки, параметр формата разметки, максимальная длина сообщения.

## 8. Слой LLM

- **`OpenAiCompatibleClient`** — универсальный клиент Chat Completions: `BaseUrl` + ключ + модель. Покрывает Yandex AI Studio и любых поставщиков с OpenAI-совместимым API; новый поставщик добавляется записью `LlmProvider` без изменения кода.
- **`GigaChatClient`** — адаптер: OAuth-обмен ключа на токен доступа (кэшируется до истечения), остальное аналогично.
- **Структурированный ответ:** промпт требует JSON по схеме; ответ десериализуется и валидируется; при ошибке — один повтор с текстом ошибки. Вторая неудача → исключение `LlmResponseInvalid`.
- **Модели по умолчанию:** Relevance/Clustering/Scoring — YandexGPT Lite; Rewrite/FactCheck — YandexGPT Pro. Меняется в настройках для каждой задачи.
- **Шаблоны промптов:** подстановки `{{city}}`, `{{sources}}`, `{{draft}}`, `{{stories}}`, `{{style}}`, `{{hint}}`.
- **Журнал:** каждый вызов пишется в `LlmCall`.
- **Бюджет:** если сумма токенов за сутки превысила `DailyTokenBudget`, LLM-задачи откладываются до следующих суток, в шапке UI растёт счётчик ошибок.
- **Повторы:** HTTP 429/5xx — через Microsoft.Extensions.Http.Resilience (нарастающая пауза, до 3 попыток).
- **Стенд сравнения (`NewsFactory.EvalBench`):**
  - `export-dataset --count 30` — выгружает сюжеты с исходниками в JSON;
  - `compare --dataset file.json --targets yandex:pro,gigachat:max` — прогоняет оценку, рерайт и проверку фактов и собирает HTML-отчёт с ответами рядом.

**Ожидаемый объём:** ~70 сырых новостей/сутки → после фильтра по ключевым словам 10–20 сюжетов → ~50–80 вызовов LLM/сутки.

## 9. Админка (SPA)

Адаптивная: ПК и телефон. Mantine, TanStack Query для запросов, `@microsoft/signalr` для живых обновлений.

- **Вход:** логин/пароль, cookie-аутентификация (`HttpOnly`, `SameSite=Strict`). Первая учётка создаётся из `ADMIN_LOGIN` / `ADMIN_PASSWORD` при первом запуске. Ограничение частоты попыток входа.
- **Шапка (все экраны):** счётчики `На проверке · Обновления · Ошибки · Сегодня X/лимит (+запланировано)`; обновляются событием SignalR `CountersChanged`. Заголовок вкладки: `(N) NewsFactory`, где N — число на проверке. На телефоне счётчики сворачиваются в значок.
- **Очередь:** вкладки *На проверке · Низкий интерес · Запланировано · Опубликовано · Отклонено · Ошибки*. Строка: оценка, заголовок, число источников, время, значок «есть обновления». Сортировка по оценке (на проверке) или по времени. На телефоне — карточки.
- **Карточка сюжета:**
  - ПК — три колонки:
    - **Источники:** название, ссылка, оригинальный текст, фото со значком «можно с подписью» / «нет разрешения»;
    - **Редактор:** заголовок, текст, хэштеги; замечания проверки фактов подсвечены; «Перегенерировать» с полем подсказки; история версий;
    - **Превью:** вкладка на каждый канал города (в MVP — Max), имитация поста площадки.
  - Телефон — вкладки «Источники · Редактор · Превью», кнопки действий закреплены внизу.
  - Под колонками: выбор фото (из источников или загрузка), «Опубликовать сейчас», «Запланировать», «Отклонить»; предупреждение о лимите.
- **Источники:** список и форма; флаги «целиком про город», «фото с подписью разрешены» + текст подписи; интервал опроса; ожидаемая частота; селекторы HTML; кнопка **«Проверить»** — холостой запуск сборщика с показом извлечённого (без сохранения); статус последнего запуска и ошибка.
- **Настройки:** город (ключевые слова, порог оценки); канал (ID чата, дневной лимит); провайдеры LLM; модель для каждой задачи; промпты с версиями; бюджет токенов; расход токенов за сегодня/месяц.
- **Служебное:** панель Hangfire `/hangfire` (только после входа).

## 10. Ошибки и надёжность

| Ситуация | Поведение |
|---|---|
| Ошибка сборщика | Изоляция по источнику; `ConsecutiveFailures++`, `LastError`; при ≥3 подряд — в счётчике «Ошибки» |
| Сайт сменил вёрстку (тишина) | Нет новых элементов дольше `ExpectedFrequencyHours` → предупреждение в «Ошибках» |
| LLM 429/5xx | До 3 повторов с нарастающей паузой |
| LLM вернул невалидный JSON дважды | `RawItem.Status = Failed` или `Story.Status = ProcessingFailed`, кнопка «Повторить» |
| Превышен бюджет токенов | LLM-задачи откладываются до следующих суток, предупреждение в UI |
| Ошибка Max API | До 3 повторов, затем `Failed`, сюжет `PublishFailed` |
| Падение во время отправки | `Sending` не переотправляется → `Unknown`, решение за человеком |
| Перезапуск контейнера | Задачи и расписание в Postgres (Hangfire) переживают перезапуск |

- **Логи:** Serilog → консоль (`docker logs`) + файлы с ротацией (14 дней).
- **Health check:** `/health` (БД + Hangfire).
- **Резервные копии:** ежедневный `pg_dump` в отдельном контейнере, хранение 7 дней.
- **Секреты:** только в `.env` (`MAX_BOT_TOKEN`, `VK_SERVICE_TOKEN`, ключи LLM, `ADMIN_*`, пароль БД). В БД — только имена переменных; UI показывает «настроено / не настроено».

## 11. Развёртывание

`deploy/docker-compose.yml`:
- **nginx:** порт `127.0.0.1:80:80`; раздаёт собранное SPA; проксирует `/api`, `/hubs` (с поддержкой WebSocket), `/hangfire` на backend.
- **api:** образ .NET 10 (multi-stage); миграции EF Core применяются при старте; тома `images`, `logs`.
- **postgres:** PostgreSQL 17, том `pgdata`.
- **backup:** `pg_dump` по расписанию, том `backups`.

SPA собирается в multi-stage образе nginx. Доступ к админке: `ssh -L 8080:127.0.0.1:80 user@vps` → `http://localhost:8080` (на телефоне — Termius/JuiceSSH с сохранённым пробросом).

## 12. Тестирование

- **Backend — xUnit, разработка через TDD:**
  - модульные: каждый этап конвейера с фейковым `ILlmClient`; детерминированная проверка фактов; конвертер в разметку Max; подсчёт дневного лимита; переходы статусов;
  - сборщики: снимки реальных RSS/HTML каждого источника в `tests/fixtures`, проверка извлечённых полей;
  - интеграционные: Testcontainers PostgreSQL, сквозной прогон «сырая новость → сюжет → черновик → публикация» с фейковыми LLM и публикатором; тест «запись в `Sending` не переотправляется»; тест склейки двух параллельных новостей в один сюжет.
- **Frontend — Vitest + React Testing Library:** превью поста, логика кнопок публикации и предупреждения о лимите.
- **Max вживую:** отдельный тестовый канал, ручная проверка перед релизом.
- **Качество LLM:** стенд сравнения (§8), не автотесты.

## 13. Границы MVP

**Входит:** всё из разделов 3–12 для одного города (Отрадный) и одного канала Max.

**Не входит** (архитектура готова):
- публикаторы Telegram и VK;
- экран управления несколькими городами (модель данных поддерживает);
- роли и права;
- push-уведомления;
- генерация картинок;
- редактирование и удаление уже опубликованного поста;
- аналитика просмотров;
- стиль редакции, привязанный к каналу.
